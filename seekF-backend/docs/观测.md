# 后端观测：指标与日志

**指标看整体数量和趋势，日志看具体发生了什么。** 先通过指标发现请求变慢、错误增多等异常，再通过日志定位原因。

## 一、指标：Prometheus 与 Grafana

### 1.1 谁负责什么

| 名称 | 作用 |
| --- | --- |
| 后端 `/metrics` | 提供当前统计数值，例如请求总数、内存和在线人数 |
| Prometheus | 定期读取这些数值，保存历史记录，供查询和计算 |
| Grafana | 向 Prometheus 查询数据，画成图表，并按规则发送告警 |

可以把 Prometheus 理解为“定期抄表并保存记录”，Grafana 则把这些记录画成曲线。

```mermaid
%%{init: {"themeVariables": {"fontSize": "14px"}, "flowchart": {"nodeSpacing": 18, "rankSpacing": 22, "padding": 6}}}%%
flowchart LR
    A[后端统计数字] --> B["/metrics"]
    B -->|定期采集| C[Prometheus 保存历史]
    C -->|查询| D[Grafana 图表与告警]
```

**是 Prometheus 主动访问后端，不是后端主动把数据推给 Grafana。**

### 1.2 Prometheus 的基础知识

#### 指标：一个有名字的数值

例如后端输出：

```text
seekf_http_requests_total{method="POST",route="/user/login",status="200"} 120
```

意思是：这个后端进程启动以来，`POST /user/login` 返回 HTTP 200 的请求累计有120次。

| 部分 | 含义 |
| --- | --- |
| `seekf_http_requests_total` | 指标名：请求总数 |
| `method`、`route`、`status` | 标签：区分方法、接口和状态码 |
| `120` | 这组标签对应的当前值 |

标签相当于分类条件。例如，同一个指标用 `status="500"` 就能单独记录返回500的请求，不必为每个接口和状态码起一个指标名。

#### 时间序列：把每次采集的数字连起来

假设 Prometheus 每30秒采集一次：

| 采集时间 | 登录请求累计次数 |
| --- | --- |
| 10:00:00 | 120 |
| 10:00:30 | 150 |
| 10:01:00 | 210 |

这就是一条时间序列：**同一项指标、同一组标签，在不同时间的数值**。Grafana 根据这些记录画曲线。

这里记录的是累计次数，不是每次采集后清零。第二个30秒增加了60次，平均每秒2次；Prometheus 不保存这60次请求各自的详细内容，具体请求需要看日志。

#### 在 Prometheus 查询结果中认识 job、instance 和 up

前面看到的是后端 `/metrics` 输出的业务指标。Prometheus 采集后，会给指标附加 `job` 和 `instance` 标签，标明数据来自哪组目标、哪个具体地址；它还会生成一个名为 `up` 的指标，记录这次采集是否成功。因此，这三个名称会出现在 **Prometheus 的查询结果中**，Grafana 查询 Prometheus 时也会用到。

例如，在 Prometheus 网页的查询输入框中输入 `up` 并执行，可能看到下面的结果（地址和采集任务名仅用于示例）：

```text
up{job="seekf-backend", instance="backend.example.com:8080"} 1
```

这里 `up` 是指标名，花括号中的 `job`、`instance` 是标签，最后的 `1` 是指标值：

| 名称 | 简单理解 | 例子 |
| --- | --- | --- |
| `job` | 一组采集目标的名称，默认来自 Prometheus 采集配置的 `job_name` | `seekf-backend` |
| `instance` | 其中一个具体目标，默认是被采集地址的主机名或 IP 加端口 | `backend.example.com:8080`（示例） |
| `up` | Prometheus 本次是否成功采集该目标 | 1成功，0失败 |

如果只想查看后端这组目标，可以查询 `up{job="seekf-backend"}`。`up` 由 Prometheus 生成，直接打开后端 `/metrics` 不会看到这个由采集方生成的指标。

**`up=1` 只说明指标采集成功，不代表支付、聊天和 AI 调用全部成功。** 同样，没有数据也不等于数值为0。

#### 三种常见指标类型

| 类型 | 怎样变化 | 本项目中的例子 |
| --- | --- | --- |
| Counter：累计次数 | 持续增加，进程重启后重新计数 | 请求总数、操作次数 |
| Gauge：当前值 | 可以增加，也可以减少 | 在线人数、内存、积压量 |
| Histogram：区间统计 | 记录有多少观测值落在各个区间 | 请求耗时 |

Histogram 可以理解为把请求耗时分组统计：不超过0.1秒的有多少次、不超过0.5秒的有多少次。区间计数是累计的，后一个区间也包含前一个区间里的请求。

根据这些统计可以估算 **P95**：约95%的请求耗时不超过这个值。例如 P95 为0.8秒，表示约95%的请求在0.8秒以内完成。

#### PromQL：用来查询和计算的表达式

PromQL 是 Prometheus 的查询语言。入门先记住几个含义：

| 写法 | 做什么 |
| --- | --- |
| `go_goroutines` | 读取当前协程数量 |
| `{route="/user/login"}` | 按标签筛选，只看登录接口 |
| `[5m]` | 使用最近5分钟的采样数据 |
| `rate(计数器[5m])` | 计算最近5分钟平均每秒增长多少 |
| `sum(...)` | 把多组结果相加 |

**QPS 就是平均每秒请求数。** Counter 当前值是累计总数，需要计算增长速度才能得到 QPS；在线人数、当前内存这类 Gauge 通常直接看数值。

进程重启会使 Counter 从头计数，`rate()` 会处理这种重置。短时间内采样不足时，可能暂时算不出增长速度。

### 1.3 本项目主要看哪些数据

| 关注的问题 | 对应指标或图表 |
| --- | --- |
| 后端还能被采集吗 | `up` |
| 请求多不多、哪些接口报错 | `seekf_http_requests_total`，通过标签区分接口和状态码 |
| 接口是否变慢 | `seekf_http_request_duration_seconds_*`，看平均耗时或 P95 |
| 有多少用户在线 | `seekf_websocket_online_users` |
| 协程或内存是否持续上涨 | `go_goroutines`、`go_memstats_heap_alloc_bytes` |
| 发现页事件是否处理不过来 | Outbox 和关注分发的积压数量、等待时长 |
| 推荐是否经常降级 | 推荐、热榜降级次数 |

HTTP 指标由中间件在请求结束后更新；Go 运行数据由采集器读取；在线人数在采集时读取当前值。业务操作次数通常在操作时累计，事件积压等则在采集时查询存储。

理解图表时注意三点：

- SSE 请求耗时是本次订阅连接持续的时间，不是模型首字耗时；HTTP 200 之后的流内错误也不会变成 HTTP 500。
- WebSocket 的 HTTP 指标记录握手，在线人数使用单独的指标。
- 部分业务指标附带 `collect_success`：1表示采集成功，0表示失败。采集失败不能当成业务数量为0。

### 1.4 Grafana 图表怎么改

仓库看板文件是 [grafana-dashboard.json](../../deploy/observability/grafana-dashboard.json)。看板中每一张图表称为一个面板。

新增面板时，选择 Prometheus 数据源，输入查询，再选择展示方式和单位，保存即可。

| 内容 | 展示方式 | 单位 |
| --- | --- | --- |
| 当前在线人数 | 单值卡片 Stat | 普通数值 |
| 内存、协程变化 | 时间曲线 Time series | Bytes、普通数值 |
| 接口耗时 | 曲线或单值卡片 | Seconds |
| QPS | 曲线 | Requests/sec |
| 错误率 | 曲线或单值卡片 | 百分比 |

例如错误率0.05表示5%，应选择0～1的百分比单位。修改后可以导出看板 JSON 保存到仓库；仓库文件修改后需重新导入，Grafana 不会自动同步。

### 1.5 邮件告警怎么工作

当前告警由 Grafana 判断并发送邮件：

```text
Prometheus 保存指标 → Grafana 定期判断 → 异常持续成立 → 发送邮件
```

邮件通知需要三部分配合：

| 配置 | 解决什么问题 |
| --- | --- |
| SMTP 发件配置 | 用哪个邮箱发送 |
| Email 联系点 | 发给谁 |
| 告警规则 | 什么情况需要发 |

Grafana 的 SMTP 需要配置发件服务器、账号、密码或授权码以及发件地址。账号信息通过部署环境提供，不在文档中填写实际值。Grafana 的发件配置与后端业务邮件配置分别管理，不会自动同步。

容器部署可通过 `GF_SMTP_ENABLED`、`GF_SMTP_HOST`、`GF_SMTP_USER`、`GF_SMTP_PASSWORD`、`GF_SMTP_FROM_ADDRESS` 等环境变量设置。修改容器环境变量时，需要按部署方式重新创建或更新容器，并保留原持久化数据；普通重启不会修改已有环境变量。

在 Grafana 的 Alerting 中创建 Email 联系点，填写收件人，先用 Test 验证邮件能够发送，再保存告警规则。看板 JSON 不包含这些单独配置的联系点和规则。

#### 一个简单的告警例子

以“后端指标采集失败”为例：

- 查询 `up{job="seekf-backend"}`。
- 条件为低于1，也就是采集失败。
- 每30秒检查一次，异常持续1分钟才正式告警。
- 选择邮件联系点；查询无数据或执行失败时，也配置为告警。

首次发现异常进入 Pending（等待确认），持续满1分钟后进入 Firing（正式告警），恢复则回到 Normal（正常）。通知还有等待和投递时间，因此不会立刻收到邮件。

原始指标 `up=1` 表示正常，而条件 `up < 1` 的判断结果为1表示“异常条件成立”，两者的1含义不同。

### 1.6 管理端依赖状态是什么

管理端的依赖状态是**后端收到管理请求后，即时检查服务能不能响应**。它不是历史图表，也不会自动变成 Grafana 告警。

检查内容包括 MySQL 连接、Redis PING、Kafka 节点信息、Elasticsearch 集群健康、Qdrant 健康检查和 Prometheus 就绪状态。六项并行检查，每项最多等待两秒。

服务能响应，只能说明这次检查通过。例如 Kafka 能返回节点信息，不代表消费者没有积压；Prometheus 就绪，也不代表后端目标采集成功。

### 1.7 开发时怎样增加指标

新增业务指标分三步：

1. **定义**：决定统计什么、用什么类型和标签。例如统计操作次数就用 Counter。
2. **注册**：把采集器加入项目现有的 `observability.NewMetrics(...)`，让 `/metrics` 能导出它。
3. **更新**：在业务结果确定的位置记录数值，例如成功后累计一次。

注册表可以理解为 `/metrics` 要展示的指标清单。**注册和更新必须操作同一个指标对象**，否则业务里加了次数，导出时却看不到。项目使用独立注册表，只注册到 Prometheus 客户端的默认注册表不会被这里导出。

标签应是有限类别，例如成功/失败、接口和方法，不放用户ID或订单号。每种标签组合都会形成一条时间序列，无限增长的标签会让数据量迅速膨胀。

还要先明确计数口径：一次文件上传重试算一次调用，每个视频分片不应直接当作一个完整文件。代码修改后编译，由用户重启后端，再确认指标是否更新。

## 二、日志：Filebeat、ES 与 Kibana

### 2.1 谁负责什么

| 名称 | 作用 |
| --- | --- |
| 后端 Zap | 将业务操作、警告和错误写入日志文件 |
| Filebeat | 读取日志文件，把新增内容发送给 ES |
| Elasticsearch（ES） | 保存日志，并提供搜索能力 |
| Kibana | 向 ES 查询日志，展示具体错误和上下文 |

```mermaid
%%{init: {"themeVariables": {"fontSize": "14px"}, "flowchart": {"nodeSpacing": 18, "rankSpacing": 22, "padding": 6}}}%%
flowchart LR
    A[后端写日志文件] --> B[Filebeat 采集]
    B --> C[ES 保存日志]
    C -->|查询| D[Kibana 查看详情]
```

### 2.2 后端怎样记录日志

业务代码调用 `zlog.Info()`、`zlog.Warn()`、`zlog.Error()` 等方法，由 Zap 将日志写成 JSON，同时输出到控制台的 `stderr` 和日志文件。主服务与 MCP 子进程都在读取配置后初始化日志；MCP 的 `stdout` 用于协议通信，日志写入 `stderr`，避免干扰通信。

日志文件位置由 `[logConfig]` 的 `logDir` 配置决定，相对路径以程序工作目录为起点。

| 文件 | 保存什么 |
| --- | --- |
| `app.日期.log` | 业务操作、调试、警告和错误等应用日志 |
| `slowsql.日期.log` | GORM 输出的慢 SQL 和数据库执行错误等日志 |

### 2.3 一条 JSON 日志怎么看

以持久化 AI 回答失败的日志为例。时间、会话 ID、错误详情和文件路径仅作示例。

```json
{
  "level": "error",
  "ts": "2026-01-01T12:00:00.000+0800",
  "msg": "持久化AI回答失败，sessionId=S示例会话: 数据库连接超时",
  "func": "user_service.(*AIChatServiceImpl).persistAndCompleteAIMessage",
  "file": "/path/to/internal/services/user_service/aichat_service.go",
  "line": 810
}
```

- `level`：严重程度。
- `ts`：发生时间。
- `msg`：操作失败的说明和原始错误。这条日志把会话 ID 拼在正文中，可以在 `msg` 里搜索 `sessionId=...`。
- `func`、`file`、`line`：日志调用位置，由封装自动补充。

JSON 的好处是字段有明确名称，便于采集和搜索。Filebeat 需按部署配置解析 JSON；仅把文件送入 ES，不代表日志里的所有字段都会自动展开。

### 2.4 该用哪个日志级别

| 级别 | 用途 |
| --- | --- |
| `Debug` | 开发调试信息 |
| `Info` | 关键流程、操作成功 |
| `Warn` | 可以继续运行的异常或降级 |
| `Error` | 操作失败，需要关注 |
| `Fatal` | 致命错误，记录后会退出进程 |

当前普通日志输出器从 Debug 级别开始记录，不会自动根据环境关闭 Debug。

编写日志时，用中文说清楚发生了什么，保留原始错误，并带上必要的业务标识。下面是为日志添加独立 JSON 字段的写法示例。

```go
zlog.Info("消息发送成功", zap.String("messageId", messageId))
zlog.Error("保存用户消息失败: " + err.Error(), zap.String("sessionId", sessionId))
```

上例使用 `zlog` 封装和 `go.uber.org/zap` 的结构化字段。不要只写“失败”或“成功”，也不要记录密码、密钥、登录 token 等敏感内容。

### 2.5 日志轮转：避免一直写同一个文件

应用日志和慢 SQL 日志都使用 `github.com/lestrrat-go/file-rotatelogs` 实现文件轮转。Zap 将编码后的 JSON 写入该库提供的文件写入器，由写入器按 `WithRotationTime` 设置的间隔切换文件，并按 `WithMaxAge` 设置的保留时间清理旧文件。

| `[logConfig]` 配置项 | 含义 |
| --- | --- |
| `logDir` | 日志保存目录 |
| `rotationTime` | 切换文件的间隔，单位小时 |
| `maxAge` | 旧文件保留时间，单位天 |

例如，间隔设为24小时、保留时间设为30天，就按该间隔轮转并清理超期文件；这些值由部署配置决定。目录在初始化时自动创建，文件输出器初始化失败时回退到控制台输出。

这里清理的是后端日志文件，ES 中已经采集的日志需要由 ES 自己的保留策略管理。

### 2.6 慢 SQL 为什么单独记录

项目给 GORM 配置了专用日志输出器，慢查询阈值为 **200毫秒**。超过阈值的查询会记录下来，便于分析接口为什么变慢；数据库执行错误也可能写入同一文件。普通 SQL 不会全部输出，查询记录不存在的错误被配置为忽略。

GORM 生成日志正文，通过 `GormWriter.Printf` 转交给 `zlog.SlowSQL`。后者调用专用的 Zap logger，将正文编码为 JSON 的 `msg` 字段，再同时写入进程的 `stderr` 和 `slowsql.日期.log`。这条输出链路统一使用 Zap 的 `Info` 方法，因此数据库执行错误的外层 `level` 也会显示为 `info`，具体错误见 `msg`。

慢 SQL 说明数据库操作耗时较长，不代表语句一定执行失败。排查时结合 SQL、耗时、错误内容和同一时间段的应用日志判断。

### 2.7 Filebeat 怎样采集，Kibana 怎样查看

后端负责写文件，Filebeat 根据配置监视新增内容并发送到 ES；Kibana 从 ES 搜索，不直接打开日志文件。

Filebeat 的采集路径、ES 地址和索引名由部署配置决定。容器部署需挂载后端日志目录，并让采集路径与挂载位置一致。例如，日志挂载到 `/app/logs` 时，可采集 `/app/logs/app*.log` 和 `/app/logs/slowsql*.log`；路径仅为示例。

在 Kibana Discover 中，选择匹配实际日志索引的 Data View（数据视图），再选时间范围，搜索错误文字或业务编号。例如，索引名使用 `app-logs-日期` 时，可以用 `app-logs-*` 查应用日志。数据视图只是指定搜索哪些索引，不保存另一份日志。

例如，Grafana 显示接口耗时升高，就去 Kibana 查看同一时段的应用日志和慢 SQL：前者帮助找到出错操作，后者帮助判断是否有耗时较长的数据库查询。

ES 在项目中也用于帖子搜索等业务，这些业务索引与日志索引分别管理。
